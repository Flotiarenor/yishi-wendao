# 提交规范（Commit Convention）

> 目的：统一提交习惯，便于 **GitHub 远程协作**时快速看懂"这次改了什么、为什么改"。
> 适用范围：本仓库。
> 依据：本仓库真实提交历史（20 条）+ 通行做法。
> 权威性：本文件只约束**提交信息**；玩法与架构仍以 `设计定案.md` / `实现路线图.md` 为准。

---

## 一、统一格式：Conventional Commits + 中文描述

```
<type>(<scope>): <中文简述>

- 改了什么 + 为什么（一行一条）
- 涉及取舍 / 风险写清楚
```

**示例**

```
feat(map): P4.5 世界地图内核——连续坐标与代价场寻路

- 新增 engine/worldmap.py：多倍频噪声地形 + A* 代价场，纯逻辑零 I/O
- 路网由城镇间最小代价路径自动生成，不手工画路
- 移动速度按地形系数：平原 22 里/日、山地 8 里/日（占位待标定）
```

```
fix(battle): 战斗结算灵石归零

- actor_from_stats 漏拷 stones → 战斗 Actor 恒 0
- _finish_battle 又用 b.p.stones 覆盖世界层，战利品先加后清零
- 改为增量扣款，只扣战斗内花费
```

---

## 二、type 取值

| type | 用途 | 例子 |
|---|---|---|
| `feat` | 新功能 | `feat(map): …` |
| `fix` | 修 bug | `fix(battle): …` |
| `docs` | 只改文档 | `docs(map): 地图与场所定案` |
| `refactor` | 重构，**行为不变** | `refactor(engine): …` |
| `perf` | 性能 | `perf(frontend): …` |
| `test` | 测试 | `test(map): test_worldmap 覆盖代价场` |
| `build` | 构建 / 打包 / 依赖 | `build: 构建脚本同步 requirements.txt` |
| `chore` | 杂项（配置 / 清理 / 忽略规则） | `chore: 补 .gitignore` |

## 三、scope（可选，推荐写）

用**阶段号**或**模块名**，保持"按阶段可追溯"：

| 类型 | 取值 |
|---|---|
| 阶段号 | `P4.5` / `P5` / `P8` |
| 模块名 | `engine` / `content` / `server` / `frontend` / `docs` / `tools` |

例：`feat(map): P4.5 世界地图内核`、`fix(engine): 修复灵石结算`。
省略 scope 时写 `type: 描述` 也可以。

## 四、subject（标题）硬性规则

1. **中文**，动词开头，写"做了什么"。
2. **≤ 50 字**；超出的细节放 body。
3. 冒号后**一个空格**：`feat(map): xxx` ✅
4. 句末**不加句号**。
5. 补充范围用中文括号：`fix(battle): 修复灵石归零（用户报"击杀后灵石消失"）`。

## 五、body（正文）规则

- 每行以 `- ` 开头，**改了什么 + 为什么**（协作时别人靠这个理解）。
- 需要分组时用小标题：`Bug 修复:` / `性能:` / `其它:`。
- **已知取舍、未修问题、影响范围**必须写明——这类信息最容易被忘、也最值钱。

## 六、footer（可选）

```
Refs: P4.5
Closes #12
BREAKING CHANGE: 存档格式变更，旧档需迁移
```

---

## 七、提交粒度

- **一个提交一件事**，能独立回滚。
- **文档与代码分开提**：`docs(map): 地图与场所定案` 与 `feat(map): 世界地图内核` 分两次。
- 一个阶段（如 P4.5）可以拆成多个提交，用同一个 scope 贯穿。

## 八、分支与远程

- 接入 GitHub 远程后：`main` 为**默认分支**，功能走 `feat/xxx` 或 `dev/xxx` 分支，合并回 `main`。
- ⚠️ **GitHub 贡献图只统计默认分支（`main`）上的提交**——长期在别的分支上提交，贡献图不会显示。
- 合并方式：功能分支用 squash 合并，保持 `main` 历史一条一提交、可读可回滚。

## 九、不要提交的东西

`venv/`、`saves/`、`logs/`、`node_modules/`、`dist/`、`__pycache__/`（按需含 `.dsh/`）。
新增产物记得同步 `.gitignore`。

## 十、历史遗留（不追溯）

本仓库早期存在以下写法，**不改写历史**（改写要 force push，代价大于收益），新提交按本规范：

| 遗留写法 | 问题 |
|---|---|
| `P3.8：效果/状态系统…` | 用全角冒号、无 type |
| `更新.gitignore` | 无 type |
| `初始提交：P0-P3.6…` | 无 type |

**形式反例（别学）**：

```
refactor:调整了部分冗余函数          ← 冒号后缺空格
chore::移除构建产物                  ← 双冒号
feat:地图支持寻路,修复若干问题,调整数值,更新文档   ← 一件事混四件 + 超长
```

## 附录：协作前检查清单

1. **作者身份固定**：`user.name` / `user.email` 不要在不同机器上换来换去。
   GitHub 只把**已验证邮箱**的提交算进贡献图；同一人被换过邮箱，会被拆成多个贡献者。
   确认方式：GitHub `Settings → Emails`。
2. **提交前跑基线**：`python main.py test`（改代码后尤其必要，见 `docs/README.md` 开头约定）。
3. **本机 git 环境备忘**：本仓库 `.git` 属主是 `BUILTIN\Administrators`（Windows 内置**组**，不是用户），
   而当前用户 SID 不同 → **非提权进程**会报 `fatal: detected dubious ownership`。
   已加入全局白名单（2026-09-10）：

   ```ini
   [safe]
       directory = D:/project/Python/yishi-wendao
   ```

   另外：若编辑器/终端以管理员身份运行，git 会跳过属主检查——这会造成"提权下正常、普通终端报错"的错觉。
