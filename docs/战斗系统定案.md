# 战斗系统定案（连续时间轴 + 双约束 + 组合式）

> 状态：✅ **定案**（2026-09-09，用户主导逐条拍板；本文件是战斗系统的唯一依据）。
> 关系：**取代** `docs/archive/技能与效果架构.md` 中"四、结算管线"的回合制部分（效果模板/修饰器
> 那套组件化内核仍然有效，作为本定案 §7 的实现基础）。
> 前提约束：引擎纯逻辑零 I/O；确定性可复现（存档回溯必须成立）；厘息整数运算。
> **进度与现状数字**（测试项数 / 指纹 / 性能等）见根 `README.md`「当前状态」事实表——**本文不重复维护**。

## 零、为什么重构（旧结构的病根）

旧 `Battle.do()` 是**命令式过程**：回合推进、灵气结算、动作分派、伤害计算、效果施加、
敌人行动、胜负判定、回合末清理全在一个函数里。后果：

| 病根 | 表现 |
|---|---|
| 规则写在流程里，不是数据 | 加"打两下""概率眩晕""对中毒目标额外伤害"都要改 `do()` |
| 没有"动作"这个一等公民 | 无法给动作附加前后摇/回灵折扣/条件/连锁 |
| 伤害公式三处手写 | 平砍/技能/敌攻各自一套参数 → 数值失衡（档18 有 6/9 攻击技弱于平砍） |
| 没有时间维度 | 速度是死属性；控制技只能"跳过一回合"，无法表达"争取时间" |
| 回合是写死的顺序 | DoT/护盾/控制没有正式插桩点，只能塞进 `do()` |

**重构目标**：层间接口冻结、层内全部数据化；加内容不改结算代码。

## 一、第一原则

1. **时间是唯一的推进维度**。没有"回合"，只有全局时间轴 `t`。
2. **速度是支配属性**（用户明确要求，非缺陷）。快 = 单位时间内动作多，这是设计意图。
3. **灵气是节流阀**：速度快不能绕过灵气，重招受灵气约束。
4. **一切时长用厘息整数**（1 息 = 100 厘息）。浮点只用于显示，不用于判定。
5. **确定性优先**：同时到达给玩家，且**不消耗随机流**；随机流按"行动实例"派生，不按调用顺序。

## 二、时间轴与推进

```python
t: int            # 全局时间（厘息）
next_t: dict      # 每个参战者的"可动时刻"

推进算法：
  while 战斗未结束:
      t = min(next_t[我方], next_t[敌方])
      if next_t[我方] <= next_t[敌方]:      # 同时到达 → 玩家优先
          开启决策窗口(长度 W = next_t[敌方] - t)
      else:
          敌方行动()
```

**同时到达的确定性**：`next_t` 相等时玩家先动，**不掷随机数**。因此相同种子 + 相同操作
必然得到相同结果（存档回溯成立）。

**随机流派生**：`rng.roll(salt)` 的 salt 必须含**行动实例标识**（如 `f"hit:{actor}:{action_id}:{seq}"`），
禁止依赖"第几次调用"。否则行动序一变，随机流错位，回溯失效。

## 三、动作模型（一等公民）

```python
@dataclass(frozen=True)
class Timing:
    windup: int = 0            # 前摇（厘息）
    recovery: int = 200        # 后摇（厘息）
    windup_speed: float = 1.0  # 前摇速度敏感度（0.0 = 完全不吃速度）
    recovery_speed: float = 1.0

实际前摇 = windup   / (1 + (速度 - 1) × windup_speed)
实际后摇 = recovery / (1 + (速度 - 1) × recovery_speed)

@dataclass(frozen=True)
class Action:
    key: str                   # 稳定键
    kind: str                  # attack / defense / utility / special
    qi_cost: int = 0
    target: str = "enemy"      # self / enemy / all_enemies（字段先留出，暂只实现单目标）
    timing: Timing = Timing()
    components: tuple = ()     # Damage / ApplyEffect / Heal / Charge / QiGain …
    conditions: tuple = ()     # 触发条件（如"目标有中毒"）
    qi_efficiency: float = 1.0 # 灵气加成系数（见 §6）
    duration_weight: float = 0.0  # 时长加成权重（见 §6）
    tier: int = 1              # 品阶（基础威力系数来源）
```

**关键：前后摇都吃速度，但比例独立、且可豁免**（`speed=0` 表示固定耗时，如遁走/捏灵石）。
这是"组合式框架"的第一处体现——框架不假设所有动作都吃速度。

**平砍/防御/聚气/遁走/捏灵石也是 Action**，不是 `do()` 里的分支。动作空间从此是开放数据集。

## 四、决策窗口与队列（无槽位）

```
我方 next_t 到达 → 开启决策窗口
  窗口长度 W = 敌方 next_t − t          ← 由敌方速度决定（快敌 = 窗口短 = 压制）
  玩家可任意插入/撤回动作，每个动作显示其结束时刻
  执行条件（OR）：
    ① 队列累计时长 ≥ W          （"摸到了下一个回合"）
    ② 玩家点击「跳过」
  执行 = 按序结算队列，我方 next_t += 队列累计时长
```

**没有槽位上限**——队列容量天然被 W 限制（"排得下 3 个平砍"是结果，不是规则）。

**跨界动作（用户拍板：允许插入）**：队列最后一个动作若跨越 `next_t[敌方]`，允许排入；
执行到该时刻时**敌方先行动**（可打断，见 §7），玩家动作照常继续结算。

## 五、资源：灵气与灵石

```
灵气（全局属性）
  上限 Q_max = f(修炼境界)          ← 用户："和你本身的修炼挂钩"
  回灵速率 R_base = g(境界, 被动)   ← 与速度无关（用户明确）
  连续累积：t 推进 Δt → 灵气 += R_当前 × Δt
  消耗：动作结算时扣除

灵石（**货币**：用灵石"买"一个灵力回复加速 ← 用户拍板 2026-09-09）
  灵石 = 货币本身，不因战斗而改变语义。
  战斗中的用法：**支付灵石，换来一个"回灵加速"效果**（相当于买了件商品/服务）。
  一次购买声明（由品阶决定，用户："低阶回复不上来，高阶昂贵"）：
    cost      ← 需要支付的灵石数量（高阶贵）
    R_boost   ← 加速效果提供的额外回灵速率（品阶越陡越高）
    T_max     ← 加速效果的持续时间（品阶越高越久）
  效果：在 [t, t + T_max] 内，回灵速率 = R_base + R_boost
  可提供的灵气总量 ≈ R_boost × T_max（派生量，不单独配置，避免三参数矛盾）
  账面：支付走正常经济扣减（与坊市买卖同一套账）。
  **加速效果不可叠加**：同一时刻只一个生效，新的覆盖旧的（用户拍板）。
```

**三层节流**（各卡不同的事）：

| 层 | 卡什么 |
|---|---|
| 灵石速率 `R_boost` | 多快能补给 |
| 灵气池 `Q_max` | 能囤多少 |
| `后摇 ÷ 速度` | 出手频率 |

**用户拍板：灵石速率不可叠加**（同一时刻只一个抽取生效，新的覆盖旧的）——否则
"多开几个"会绕过速率上限，重招的灵气节流失效。

**"低阶不够用、高阶昂贵"** 由两个维度表达：低阶 `R_boost` 低且 `T` 短；高阶 `R_boost` 高、
`Q_total` 大 → 是真正的"战斗资本"。

## 六、伤害：五段乘区（技能分化在这里）

```
伤害 = 基础威力
     × 灵气加成        # 1 + 投入灵气 × qi_efficiency
     × 时长加成        # 1 + (实际总时长 ÷ 基准时长) × duration_weight
     × (1 − 减伤)      # 减伤 = 防御 ÷ (防御 + K)
     × 五行            # 克环
     × 状态            # 攻方乘区 × 守方乘区
     × 随机浮动        # ±10%

基础威力 = 技能基础威力 × 品阶系数(tier)
```

**灵气加成是"基本线性"的**（用户拍板），且 `qi_efficiency` 是**技能自身属性**。
这条是"技能释放方式 × 灵气属性"的落点，也是流派来源：

| 流派 | 吃哪个维度 | 机制 |
|---|---|---|
| 引气流 | 灵气 | `qi_efficiency` 高 → 灵气越多越猛，受池上限约束 |
| 品阶流 | 品阶 | `qi_efficiency` 低但 `基础威力×tier` 高 |
| 蓄力流 | 时间 | `duration_weight` 高 + 前摇可延长 → 用时间换威力 |

**"威力 ∝ 时长"不是硬规则**（用户明确）：时长加成只是可调权重之一，与灵气、品阶并列。

## 七、效果：时间窗口语义（替换 duration=1 的"回合"）

```python
@dataclass
class EffectInstance:
    key: str
    start_t: int          # 生效时刻
    end_t: int            # 失效时刻（时间窗口，不再用"回合数"）
    stacks: int = 1
    params: dict = {}
```

- **状态效果 = 时间窗口**，到期按 `t` 判定，不再依赖回合 tick
- **前摇被打断（用户拍板）**：

```
动作前摇期间处于"未落地"状态
  期间自身被控制（定身/晕眩）→ 前摇中断、动作取消
  期间对手动作先落地 → 按时间先后结算，可能打断
  ⇒ 谁的前摇先完成，谁的效果先落地（出手顺序 ≠ 结算顺序）
  中断代价：退灵气 + 算后摇（用户拍板）
```

**控制技的战略价值**从"减伤"变成"让对手的投入打水漂"——这是时间轴模型的原生语义。

**控制 = 推后对手的 next_t**（定身/晕眩/迟钝统一为一个参数，不同表现）：
- 定身：推后 next_t，不附加状态
- 晕眩：推后 next_t + 附加 `vulnerable`（受击加成）
- 迟钝：提高对手后续动作的实际时长（降速）

## 八、引擎分层与接口契约

```
engine/clock.py     时间轴推进器：厘息整数、同时到达仲裁、确定性、窗口计算
engine/action.py    Action/Timing/Component 模型 + 执行器（解释数据，不含具体技能逻辑）
engine/status.py    状态行为注册表：damage_mult / hit_negate / push_back / speed_mult（P4-R4）
engine/rules.py     纯函数：resolve_damage / 命中 / 减伤 / 状态乘区（无状态、可单独单测）
engine/battle.py    决策窗口 + 队列执行 + 阶段钩子（只调度，不含技能逻辑）
content/actions.py  动作数据（平砍/防御/聚气/遁走/捏灵石/各技能）
content/effects.py  效果模板（时间窗口语义）
```

**接口冻结**（层间契约，改动需走定案修订）：
- `content → engine`：只传数据对象，engine 不 import content 的具体技能
- `engine/rules.py`：纯函数，入参 → 出参，无副作用
- `engine/battle.py`：对外只暴露 `step()` / `state_data()`，内部阶段可插桩
- **伤害唯一入口**：全项目只允许一处 `resolve_damage` 调用路径

## 十、验收原则

1. **确定性**：同种子 + 同操作序列 → 逐位相同；回溯后重放结果一致（随机流按行动实例派生）
2. **层间解耦**：新增技能 = 只加 `content/actions.py` 数据，`engine/` 零改动
3. **伤害唯一入口**：静态检查/测试断言全项目只有一条结算路径
4. **前摇中断语义**：有专门单测覆盖（退灵气 + 算后摇 + 动作取消）
5. **时间窗口效果**：DoT/护盾/控制按 `t` 到期，不依赖回合
6. **等价性策略**：本次重构**不追求行为等价**（回合制→时间轴本质不同），
   改为**重建基线**：新单测 + 新 smoke 指纹，并记录"旧基线作废"的决策

### 十一之一、木桩实测发现的**尺度问题**（2026-09-09，已标定）

**问题**：初版占位数值下，灵气几乎不构成约束，"速度支配 + 灵气节流"里的**节流失效**，
灵石加速也看不出效果。证据（焚天火海初版：耗灵 30、周期约 7.5 息）：

| 回灵速率 | 周期内可得灵气 | 实测 DPS |
|---|---|---|
| 3/息（初版基础） | 22.5 | 38.3 |
| 3+15/息（加速） | 135 | 38.3（**无变化**） |
| 3+30/息 | 247 | 38.3（**无变化**） |

**根因是尺度，不是结构**：

```
要让灵气成为约束，必须满足：  技能耗灵 > 回灵速率 × 该技能的实际周期
```

**标定（用户拍板 2026-09-09：qi_rate 降低、灵气池不变、技能耗灵提高）**：

| 项 | 初版 | 标定后 |
|---|---|---|
| `qi_rate`（木桩基准） | 3/息 | **1/息** |
| 灵气池 `qi_max` | 100 | **100（不变）** |
| 引气流大招（焚天火海） | 耗灵30 / 威力30 | **耗灵40 / 威力60** |
| 引气流中技（千剑诀） | 耗灵20 / 威力20 | **耗灵40 / 威力60** |
| 品阶流（锐金剑气） | 耗灵9 / 后摇300 | **耗灵4 / 后摇200** |

**标定后木桩实测（30 息窗口、木桩防御 20、玩家攻40/池100/回灵1.0）**：

| 流派 | DPS | 说明 |
|---|---|---|
| 灵石加速流 | **51.2** | 花 400 灵石，加速后大招连发 |
| 引气流 | 31.7 | 靠聚气撑，不买加速明显掉档 |
| 品阶流 | 20.4 | 低耗高频，完全不吃加速 |
| 蓄力流 | 19.3 | 长前摇换威力 |
| 平砍基准 | 16.5 | 地板 |
| 低血流 | 26.1（低血时） | 满血时焚身被拒 → 16.5（以生存换输出） |
| 控制+条件流 | 10.5 | 辅助换输出，符合定位 |

**加速的边际效果已验证**（焚天火海，qi_rate=1）：无加速 39.0 → +15/息 **58.5**（+50%）。
且**低耗灵技能不吃加速**（后摇主导）——`test_action.py` §9 已锁这两条不变量。

⚠️ **标定红线**：不要再把引气流大招耗灵调回 30 以下（= 基础回灵 × 周期），否则加速边际归零，
"灵石加速流"会与"引气流"同分。这条由单测锁住。

## 十三、实现前必须敲定的细节（已定）

**1. 灵石 = 用货币买"回灵加速"（✅ 用户拍板 2026-09-09）**
灵石是货币；战斗中的用法是**支付灵石，换来一个回灵加速效果**（相当于买商品）。
加速效果在 `[t, t+T_max]` 内把回灵速率提升到 `R_base + R_boost`。
"低阶回复不上来、高阶昂贵"由 `R_boost` 与 `T_max` 两个维度表达；`cost` 由品阶决定。
账面走正常经济扣减（与坊市同一套账）。**加速不可叠加**（同一时刻只一个生效，新的覆盖旧的）。

**2. 跨界动作与打断是同一机制（✅ 按倾向定）**
队列跨界时敌方先行动，敌方行动**可能打断队列中正在前摇的动作**（§7 规则同样适用）。
即"跨界"与"被打断"统一按时间先后结算，不引入第二套规则。
