## 三、设计思路（为什么这么做）

### 3.1 舆图必须"低精度"，这是**语义**不是画风

用户一句"舆图哪来的能力测高差和分区块"直接定死了这套渲染的语义边界：

| 别画 | 为什么 |
|---|---|
| **高程明暗（测高差）** | 那是等高线/晕渲的语言。古代舆图没有高程数据 |
| **地形色块分区** | 那是遥感/专题图的语言 |
| **深海 vs 浅海** | 同样测不出海底高差——**分了深浅等于假装知道** |
| **精确岸线** | 舆图的海岸是"大致如此" |

**所以舆图层的规则是**：单色墨 + 纸底 + **粗粒度地貌母题**（海=波浪、山=山尖+侧脊、
沙=点阵、草=草簇、林=小松、沼=芦线、禁制=圈×）+ 拟合路网 + 城镇墨点 + 主城地名。
**而"实景层"（`tools/maprender.py`）才是色块 + 明暗 + 精确路网**——两层语义分别是
"**我听说过/买来的**"与"**我亲自到过的**"。这正好接上定案 §5 的两层迷雾。

> 这条给后续的启示：**地图上的每个视觉元素都是一条"世界知识"的声明**。
> 画得越精确，就越是在假装角色知道得越多。以后加图层先问"这个知识，角色从哪来"。

### 3.2 LOD 与探索边界：为什么不是"缩放级别"分层

实测硬约束：**细档（逐像素连续采样）耗时只与输出像素数有关**（600 里与 6000 里视野都是 ~52s
@1280px），所以"缩小时用低清"**省不了时间**；而**快档（读引擎全图数组）只要 0.1s**。

于是分层按**探索状态**而不是缩放级别：

```
底图（快档，0.1s，天然实时）         = 舆图风，覆盖全图
高清块（按需渲染 / 离线预生成后缓存） = 实景风，只覆盖 discovered / places 走过的地方
分界线 = T4 已有的 discovered 集合（不新造状态）
```

**为什么这条能成立**：舆图风是**逐格**扫描（400×400 = 16 万格），与输出像素无关；
实景风是逐像素，贵，但它只需要覆盖"走过的那几块"。**两层各自用自己最便宜的画法。**

### 3.3 地图为什么必须由**后端**渲染（而不是浏览器画）

| 方案 | 问题 |
|---|---|
| 浏览器逐格画 16 万格 | 必卡；且 18 种地形 + 母题 + 纸纹是**绘图密集**工作 |
| 浏览器画 SVG 矢量 | 现方案；但画不出"地形"（现在只画了点），也没有离线渲染能力 |

后端 pygame 渲染的优势是**实测出来的**：舆图风 1200px **0.10~0.37s**（有 LRU 缓存），
且**同一份渲染器可离线出图**（`tools/atlas.py`）→ 可纳入 `tools/`、可做像素回归。
**分工定死**：后端出"静态底图"，前端 SVG 层继续管"交互"（点选/悬停/右键/候选路径）——
**不要把交互搬进渲染**，否则要自己写命中测试，得不偿失。

### 3.4 音频为什么归**宿主进程**（与壳无关）

实测（CoreAudio 会话枚举 + 设备峰值表，真实音频）：

| 谁在播 | 会话归属 |
|---|---|
| 网页 `<audio>`（pywebview 或 **C# 壳**都一样） | `msedgewebview2.exe` |
| **宿主进程**打开音频设备 | **我们自己的进程** |

两条结论：① **归属跟着"谁打开音频设备"，与壳技术栈无关**——所以为了音量合成器换 C# 是白换；
② 网页停音后 WebView2 那条会话**不会消失，只转非活跃**；两边同时播会真的出现两个条目。

**故定规则**：**音效/BGM 一律宿主进程播、网页侧永不播音频**（随之：前端音量滑块不能直接调音量，
必须经 HTTP 回宿主——这条在做音效前就要进契约）。

### 3.5 桌面壳的"身份"要拆成四件事看

| 表现 | 由谁决定 | 我们做到了吗 |
|---|---|---|
| 标题栏 / Alt-Tab 名 | 窗口 title | ✅ |
| 任务栏图标 | 窗口图标 / exe | ✅ `assets/app.ico` |
| 任务栏分组 / 固定 / 通知归属 | **AppUserModelID** | ✅ 显式设置 + 快捷方式写同 AUMID |
| **音量合成器里的名字** | WebView2 宿主进程 | ❌ **改不了**（上游限制）——但按 §3.4 可由"宿主播音频"绕过 |

**全屏/置顶/托盘/通知**属于前三行的范畴，**都能控**（`win.native.Handle` + Win32），
**不需要换壳**。真正该换壳的时机是"要发一个 exe 给不装 Python 的人"——那是**分发形态**驱动，
不是音量合成器驱动。

### 3.6 为什么最后用 Selenium（而不是继续修 jsdom）

jsdom 有**两个原理性盲区**，而这次全都撞上了：

1. **不加载图片资源** → 舆图底图在 jsdom 里**从不被请求、从不被绘制**，
   于是"图到底画出来没有、像不像舆图"**根本无法验证**（我也读不了图，等于全盲）；
2. **是模拟 DOM** → 点击不判断可操作性。冷启动（建世界 6~10s）期间按钮 `disabled`，
   点下去**会被直接丢掉**，只能靠手写"点到生效"重试来兜——那套测试的抖动根因就在这里。

Selenium + **真 Edge 152.0.4191.66（与游戏分发的 WebView2 同版本）**同时解决两点，还给了
**截图**与**像素级断言**的能力。

**但结论是"分工"而不是"替换"**：jsdom 那套快（~30 项逻辑/契约断言），保留；
Selenium 只放**jsdom 做不到**的少数几条（能否真渲染、CJK 字体、真交互）。

## 四、误区与教训（**最值钱的一节**）

### 4.1 傅里叶拟合"短折线"必然爆炸（用户实测发现"满屏乱画直线"）

- 现象：地图上出现大量**变化率极大的直线**，路网完全不对。
- 根因：路网折线**多数只有 5~9 个点**（205 段里 59 段 7 点、39 段 9 点、22 段 5 点），
  截断傅里叶级数在样本极少时**剧烈外插**——实测 5 点/241 里的折线被拉成 **29968 里（124×）**，
  最差 **386×**。**傅里叶只适合长序列。**
- 第二次也错：改"向心 Catmull-Rom"仍 6.7×——我把**局部 t 区间**与**全局结点 τ** 混用，等于沿 τ 外插。
- 最终：**均匀参数化 Catmull-Rom**（标准 Hermite，t∈[0,1]，过冲有界）→ 全长膨胀 **1.000~1.019**，
  平滑点到原折线**最大偏离 6.6 里**。
- **教训**：① 平滑/拟合前先看**样本量**；② 用**几何不变量**验收（长度比、最大偏离），
  别用"看着还行"；③ 手抖（wobble）是第二个乱画来源，**默认关**。

### 4.2 "后台预热"是**净亏损**（我自己造的坑）

- 想法：新局时后台把地图底图渲好，玩家点开即得。
- 实测：舆图渲染只要 **0.37s**，但预热线程要先**建世界（≈6s）**且长时间持 GIL →
  把 `/api/new` 从 6~8s 拖到 **11~24s**（用户可见事故，还把 E2E 时序搞崩）。
- **教训**：**"便宜的东西"不要塞进"昂贵的路径"**；要预热也要先量"预热自身要付什么"。
  已撤（`_prewarm_map` 保留为 no-op 并写明原因）。

### 4.3 白吃一份世界生成

底图渲染原本自己 `WorldMap(seed)`，与会话那份**不是同一个实例** → 首次取图 **13.4s**。
改为**复用会话的 `wmap`** → **0.74s**。
**教训**：跨模块共享同一份"昂贵且确定"的对象（这里是世界实例）要显式传。

### 4.4 E2E 的固定 `sleep` 顶不住冷启动（既有脆弱性）

- 现象：同一份代码多次连跑得到 **31/0、23/3、20/6** 交替；失败项位置每次都不同。
- 定位：用仓库原版 E2E 在同一代码上复现 → **属既有脆弱性**，成因是
  **服务端冷启动建世界 6~10s，而测试里大量"固定 sleep"**。
- 已修：把 `sleep` 换成 **"等真实结果"**，并新增 **"点到生效"**（`clickUntil`）吸收"点击被丢"。
- **未根治**：仍有偶发；根治 = 剩余判定全改"等结果"或整体迁 Selenium。
- **教训**：E2E 里**任何 `sleep(>300ms)` 都是潜在误报**；`sleep` 只该用在等动画。

### 4.5 我用"像素统计"替你验收图片（因为读不了图）

当前模型不支持图像输入，所以舆图效果一直是靠**颜色占比/构成/颜色数**去核对的
（例如"纸底 11.4%、水蓝 1.8%"），**不是"我看了觉得好看"**。
Selenium 截图同样是为**你**看的。**别把我的统计当成审美结论。**
