## 三、设计思路说明（"为什么是这样"）

### 3.1 代价模型：为什么必须"代价域线性组合"

**旧实现**：危险惩罚乘在**速度域**（`mult = 1 + 3×danger`），而每格又取 9 点采样的**最小代价**
→ 格内只要有一点好地形，惩罚就被 `min` 抹平。实测：危险权重从 3.0 扫到 100，
路径的危险地形占比反而 **86% → 99%**、耗时翻 70 倍——**惩罚结构性失效**。

**定论**：
```
格代价 = 时间项(息) + danger_w × danger × 里程 + route_pen × 里程 + exposure_pen × exposure × 里程
```
三项**同量纲（息）**，`min` 不再抹平。`danger_w` 等参数是 **profile 参数**（不再是硬编码 3.0）。
A\* 启发式必须**同步加惩罚下界**（`_heuristic_danger_pen`），否则不再是可采纳的。

**踩过的量纲坑（已写进代码注释）**：代价单位是**息**，每 50 里的时间项是 **4.9×10⁴~5.4×10⁵ 息**。
把 `danger_w` 按"天"写（1.5）→ **小 43 200 倍**，惩罚静默失效，标定扫描全是噪声。

### 3.2 移动：时间接真 + 两段式 + 不自动绕行

- **唯一时钟**：世界/战斗/移动共用 `GameState.t`（息）。移动耗时 = **路径积分** `PathResult.total_si`，
  `TRAVEL_DAYS`（固定 3 日）退役。
- **两段式 `travel`**：不带 `route` = **纯查询**（给候选，不推进时间/不移动）；带 `route=N` = 执行。
  这是"给玩家选择"与"状态可预测"的前提（前端能先算后走）。
- **手动探路 `march <八方向>`**：直线推进、**遇硬阻挡与水域停下问玩家**、**绝不自动寻路**
  ——"无舆图"的核心语义就是"玩家自己承担绕行代价"（定案 §4.2）。
- **档位按舆图给**：`none` 只许 `march` / `coarse` 1 条候选 / `detailed` 3 条（定案 §5）。

### 3.3 存档：位置真相与世界缓存

- **`WorldState.pos` 是位置真相**；`Player.location`（旧地点 id）降级为**派生标签**
  （前端契约 / smoke / 旧测试都用它，故保留 int id 语义）。
- `world` 键**恰 6 个**（`world_seed/pos/discovered/places/world_diff/map_level`）；
  地形/路网/城镇/内容点**一律不存**，纯函数重建（定案 §7）。
- 老档（无 `world` 键）→ `WorldState.legacy(seed, location=旧地点名)` → 锚点坐标。

### 3.4 性能：为什么"移动接真"会引爆三个坑（都修了）

移动一旦访问世界，就把三个潜伏的性能问题暴露出来了：

| 坑 | 根因 | 修法 | 效果 |
|---|---|---|---|
| **建路 98 s**（部分 seed） | `_build_roads` 对**必然无路**的城镇对反复跑全图 A\*（16 万格/次，408 次） | `coarse_components()` 连通性预筛——**与 `cost_field` 同粒度**（每格 3×3 采样全通才算通） | **98 s → 3.4 s**，路径结果**逐位不变** |
| 旧地点互访也建世界 | `_travel` 无条件寻路 | 旧地点之间走**固定连接**语义（不建世界）；真实城镇才寻路 | 每次挪步不再付 6 s |
| `state_data` 变慢 | 每次快照都遍历 206 座镇算位置标签 | 地名在**移动落地时算一次**存进 `WorldState.places`；首访世界时算好城镇半径表 `_town_rl` | 快照回到 O(1) |

> **通用教训**：`_ensure_*` 是惰性的，**"谁触发它"决定了成本落在哪**。写新调用点时先问自己
> "这一步会不会把 6 秒的世界生成拖进玩家的一次点击/一次状态快照里"。

### 3.5 内容点：为什么"城镇周边优先"用格距而不是欧氏距离

- **动机**：出生城视野 66 里内**一个内容点都没有** → 出门无事可做（实测）。
- **做法**：`_town_dist_cells()` 多源 BFS 求每格到最近城镇的**格距**，400 里内概率 ×1.9。
- **为什么用格距**：欧氏距离含浮点运算，**会随路径/求值顺序漂移**，破坏"同种子逐位一致"的世界指纹；
  格距是整数 BFS，绝对确定。
- **倍数 1.9 怎么来的**：**总量守恒**标定（城镇周边格约占总陆地 41%）——
  改造前 1278 个 → 改造后 1385，出生城 400 里内 3 → 13 个。**这是用户拍板的方向**。

### 3.6 城镇布局：为什么"要素层 + 分区层"两层

| | **要素层** | **分区层** |
|---|---|---|
| 语义 | **"这个坐标上有这个东西"** = 事实 | **"这一片是干嘛的"** = 意图 / 留位 |
| 谁消费 | **引擎**：判定"你在坊市吗"、开面板、能否通行 | **生成器 + 以后的内容**：这片该长什么、以后填内容 |
| 玩家交互 | **能**（这就是交互点） | **不能**（氛围/分类，本身不是设施） |

- **一个设施 = 一块连通的同类格子**（4 邻接洪泛合并）：**3×3 坊市算 1 处、开 1 个面板**。
  玩家站在其中任意一格都算"身处该设施"。
- **可达性按设施整体判**：只要设施**外沿有一格挨路**即可进入。
  ⚠️ 早期逐格判"每格 2 格内有路吗"→ **3×6 大客栈的内部格全被标为"走不到"（假警报）**。
- **城内应铺满**：除交互设施与道路外不留白（用户要求）→ 「填满城内」生成器 + 体检"城内留白"项。

### 3.7 标注工具的判据必须与引擎**同口径**

工具会输出"体检结果"，而引擎按它决定"这份布局能不能用"。**两边判据不一致 = 导出的体检会骗人**
（实测发生过：工具逐格判 vs 引擎按设施判）。现约定：

- 设施识别：4 邻接洪泛 + 按设施整体判可达（工具 `facilitiesDetailed()` ≡ 引擎 `TownLayout.facilities()`）
- 道路分段：**区分城内/城外**——城外碎引路本来就该独立，不算硬伤
- 城墙撞穿：**不能写死 `y===2 / y===H-3`**（墙挪位置就漏报）；城门不能按坐标猜朝向
  （这两条都实际踩过，见 `docs/审查-town_editor-v3.md`）
- 回归入口：`node tools/run_town_diagnose.js <json>` 直接打印工具对该布局的判定

```
   城镇布局改动必须 `node tools/run_town_diagnose.js <json>` 过一遍
```

**改地图时的铁律**：

- 改动会**改变世界内容** → `terrain_checksum` 与 G/D 组断言需重基线，属预期
- **不要**把路/河写回地形数组；**不要**再引入全图高精度数组
- **不要**在 `_ensure_*` 之前读 `_elev`（首次为 `None` → 惩罚静默失效，踩过）
- 每次改完必须跑 `main.py test` 全量 + smoke，确认指纹变化是否**故意**
- **不要**为"省内存/省延迟"做优化——先量再说：当前量级（单世界 3.2 MB、寻路 ≤0.87 s、
  玩家一次操作 ≥1 s）下多数"优化"是伪优化
- **判据要跟引擎同口径**：工具报的体检结果会被引擎当依据，两边不一致 = 骗人
