## 二、复核补出的四处代码事实（上一份交接未列，T4 直接踩）

上一位交接的「引擎侧已就位：`map_view()` 按档下发、`vision_li` 已算、`discovered` 已存」
**方向正确但偏乐观**，本次查到四条具体事实：

### 2.1 `discovered` 目前**只读不写**——所以「已知」恒为假

全库检索 `discovered`：`engine/game.py` 只在 `map_view()` 里**读**它（`disc = self.state.world.discovered`）与
**序列化**（`WorldState.to_dict/from_dict`）；**没有任何写入点**。`step("debug", key="map")` 只改 `map_level`、不写 `discovered`。
→ 后果：`map_view()` 的 `known` 字段**永远只由神识视野决定**，`counts.known_points` 的语义是
"视野内点数"，不是"已发现点数"；一旦离开视野，点又变回「（未探明）」。
→ **T4 的第一件事就是给它一个写入路径。**
> ✅ **已修（2026-09-11）**：新增 `Game.discover_here()`，挂在 `travel`（两处落地）/ `march` / `explore`
> 的落地点；`data.newly_discovered[]` + `discovered_total` 下发到前端。见 `docs/实现路线图.md` P4 节。

### 2.2 `WorldMap.visible_points()` 是**死代码**，而 `map_view()` 自己重写了一遍判定

`engine/worldmap.py:visible_points()` 有完整实现（半径 + 地形遮蔽 + `discovered` 过滤 + 距离排序，单测 H53–H56 覆盖），
但**调用点只有测试**（`tests/test_worldmap.py`）。`map_view()` 走的是自己的循环 + `Game._in_vision()`。
→ 同一个语义**两处实现**。这与上一位交接 §3.7 立下的"判据必须与引擎同口径"是同一类风险——
**建议 T4 收敛成一处**，否则"视野内算已知"和"落地写 discovered"很容易用上两套半径。
（本次核对：两处当前**口径等价**——`_in_vision` 用 `terrain_at_cell(cx,cy)`，`visible_points` 用 `_terrain_cell(cx,cy,True)`，
而 `terrain_at_cell` 内部就是 `_terrain_cell(cx, cy, True)`，都取格中心地形；差异只在写法，不在结果。）
> ✅ **已收敛（2026-09-11）**：`map_view` 的「已知」判定改为 `visible_points()` 的结果集
> （`vis_ids`），不再自己算半径；`_in_vision` 保留为等价单点问法并注明口径来源，
> `discover_here()` 也一律走 `visible_points()`——**视野语义现在只有一处实现**。

### 2.3 `map_view` 缓存键含 `len(disc)` → **discovered 一开始写入就会返回过期结果**

`engine/game.py:1160`：`key = (round(x,1), round(y,1), lvl, realm, len(disc), rad)`。
用**集合长度**当版本号，只在"只增不减且每次加一个"时才勉强成立。T4 一旦实现
"买图批量写 / 落地按批写"，同位置短时间内**批量新增**仍然会变长度（能失效），
但若出现"加一个、减一个"（例如以后的失窃/遗忘/重置情报）就会**长度相同 → 命中旧缓存 → 静默显示过期迷雾**。
→ **改法**：换成 `WorldState` 上的 `disc_version: int` 单调计数器（或把 `frozenset(disc)` 放进键）。
这是 T4 的**前置小修**，建议和发现机制同一提交做掉。
> ✅ **已修（2026-09-11）**：改为 `Game._disc_ver` 单调计数器（`discovered` 每变更 +1，
> **不存档**、只作缓存失效用）。回归用例见 `tests/test_fog.py` C3。

### 2.4 `map_level` 的档位语义**与定案 §5 有分歧**，需要在 T4 里拍板

- **代码现状**（`map_view()`）：
  - `none` → **只给自身坐标**（城镇也看不见）；
  - `coarse` → 给**周边城镇**（名字/里程/到没到过/在不在此）；
  - `detail` → 再加**内容点**（视野内 + 已发现，未探明只给轮廓）与河流大势。
- **定案 §5 里的两层迷雾**：**舆图层**（山川大势、域界、**城镇方位**）**开局即有**；
  **实地层**（矿脉/灵草/兽巢/遗迹/秘境入口/小径/驿站）**未知，需揭示**。
- → 即：**"看得见城镇"不该由舆图档决定**（它是舆图层），**舆图档决定的是"能不能看到内容点那一层标注"**。
- 另：开局默认档是 `coarse`（`engine/game.py:480` 注释"定案 §5"，老档 `WorldState.legacy` 也是 `coarse`），
  但定案写的是"**开局即有舆图**"而非"开局有**粗**舆图"——**开局档位本身也是待拍板项**。
> ⏸️ **已拍板（2026-09-11，用户）**：**保持代码现状**——`none` 连城镇也看不见，
> 开局档位保持 `coarse`。**与定案 §5「舆图层开局即有」的差异作为已知欠账记录**，
> 不在 T4 里改（改动会波及 `travel` 可用性与 smoke 指纹）。回归用例见 `tests/test_fog.py` E7/E8。

### 2.5 顺带确认的两条"已就位"（这两条上一位交接说得对）

- **`_set_pos_arrived()` 是移动落地的唯一收口**（`engine/game.py`，调用点仅 3 处：两段式 `travel` 执行、旧地点近距移动、`march` 落地）。
  → **"落地必探"钩子挂在这里，一次覆盖全部移动方式**，不必碰 `travel`/`march`/`explore` 各写一遍。
- **`state_data()["map"]` 已挂 `map_view()`**，前端 `MapScreen.vue` 已在消费
  （`map_level` / `vision_li` / `points[].known` / `name_shown` / `counts.known_points` 均已渲染，含"未探明"文案）。
  → **T4 引擎侧一写完，前端不用改就能看见效果**（这正是本次建议先做引擎侧的理由）。
