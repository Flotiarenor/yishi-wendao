## 二、对外 API（冻结）

### 2.1 战斗对象

```python
# engine/battle.py（重写）
class Battle:
    def __init__(self, player_stats: dict, player_actions: list, enemy, rng,
                 seed_salt: str = ""):
        """player_actions: 可用 Action 列表（由 game.combat_actions() 备好）
        rng: 复用 Game 的 Rng（随机流由本层独占，按行动实例 salt 派生）
        """
    # ---- 查询（前端/测试只读） ----
    def state(self) -> dict            # 战斗快照（见 §2.3）
    def pending(self) -> list          # 已排入但未执行的队列
    def timeline(self) -> list         # 已发生的行动记录
    # ---- 提交与推进 ----
    def submit(self, action_key: str, target: str = "enemy") -> tuple[bool, str]
    def skip(self) -> tuple[bool, str]        # 玩家点「跳过」→ 立即执行队列
    def run_window(self) -> list               # 执行队列 + 推进时间轴到下一个决策点
    # ---- 结算 ----
    def outcome(self) -> str                   # "" / win / lose / fled
    def ended(self) -> bool
```

### 2.2 `game.py` 层

```python
# 新增动作（保留旧名 battle_action 作兼容别名）
"battle_submit" {action, target}   # 入队一个动作 → 返回队列快照
"battle_skip"   {}                 # 执行队列并推进
"battle_action" {cmd, skill_id}    # 兼容别名：等价 submit + 自动 skip
```

**兼容策略**：旧调用 `step("battle_action", cmd="attack")` 语义 = 提交平砍并立即执行
（= submit + skip）。这样 smoke/CLI/旧测试的循环写法**不需要大改**，只是每次调用
都会推进一个决策窗口。新前端改用 `battle_submit` + `battle_skip` 做队列编辑。

## 三、主循环（阶段机，顺序冻结）

### 3.1 「一个决策窗口」的边界

```
窗口开始 = 玩家 next_t 到期的时刻
窗口结束 = 玩家下一次 next_t 到期的时刻（或战斗结束）
  —— 期间敌方可能行动多次（敌方 faster），玩家队列可能被中途打断
```
即：**玩家只负责"排这一轮要出的招"，引擎负责把这一轮跑完到玩家下次可动**。
这保证每次 `run_window()` 返回时，玩家一定处于"可以决策"的状态，前端逻辑简单。

### 3.2 执行流程

```
run_window():
  1. 校验队列非空且总时长 ≥ window_li（或玩家显式 skip）
  2. 按队列顺序逐个执行动作：
     a. 前摇：登记落地事件（时刻 = t + 实际前摇）
     b. 若前摇期间被打断（自身被控制 / 对手动作先落地且造成控制）→ 取消：
        退灵气 + 计后摇 + 记 timeline（定案 §7）
     c. 前摇结束 → 组件结算（伤害/状态/回灵/购买）
     d. 后摇结束 → 该方 next_t 推进
  3. 队列执行期间若跨过敌方 next_t → **敌方行动插入**（按时间先后）
  4. 双方交替推进，直到：
     - 一方 HP ≤ 0 → 结算
     - 时间轴到达玩家下一个可动时刻 → 返回（等待新决策）
  5. 返回本窗口的 timeline（叙事 + 结构化）
```

**时间推进粒度**：以"下一个事件时刻"（玩家前摇落地 / 敌方行动 / 效果到期）为步进单位，
不做固定 dt 轮询——保证精确且高效。

## 四、敌方行动（用户拍板：统一为"灵兽进攻"）

**不做每敌独立技能表**。所有敌人共用一个通用进攻动作 `enemy_strike`，参数由敌人数据驱动：

```python
# content/actions.py
ENEMY_STRIKE = Action(
    key="enemy_strike", name="扑击", kind="attack",
    timing=Timing(windup=100, recovery=300),      # 前摇 1 息 → 给玩家打断/防御窗口
    components=(Damage(power=0, attack_ratio=1.0, element="无"),),  # 威力来自敌人 attack
    qi_cost=0,
)
```

- 敌人**不做灵气系统**（无 `qi_cost`）：它们是灵兽/傀儡，只有节奏
- 敌人**速度**决定其实际 `recovery` → 快兽压迫感来自时间轴，不是技能花样
- 敌人**五行**来自 `Enemy.element`，乘区照常生效（玩家可用克制反制）
- 未来要分化敌人：只加 `Action` 数据 + 在 `Enemy` 上挂 `action_keys`，**不改战斗层**

**节奏基线**（占位）：灵兽 前摇 100 / 后摇 300 厘息 → 每 4 息一次扑击；
快兽（speed 2.0）→ 每 2 息一次；慢兽（speed 0.5）→ 每 8 息一次。

## 五、打断规则（定案 §7 的落地）

| 事件 | 处理 |
|---|---|
| 前摇期间自身被 `root`/`stun` | 动作取消：**退灵气 + 计后摇**（用户拍板） |
| 前摇期间对手动作先落地 | 按时刻排序结算，对手效果可能触发上面的取消 |
| 前摇已完成 | 效果落地，不可被打断 |
| 队列跨界 | 敌方插入行动，同上 |

**实现要点**：前摇不是"睡一段时间"，而是**登记一个落地事件**；执行器按时间序处理事件，
处理到"控制类效果施加"时，检查受影响方是否有未落地的动作 → 取消。

## 六、确定性（必须保证）

```
随机流 salt = f"{battle_id}:{actor}:{action_key}:{seq}"
```
- `seq` = 该场战斗内该方第几次行动（单调递增，不入存档但由战斗内计数保证）
- **禁止**依赖"第几次调用 rng"——敌方插入/打断都会改变调用次数
- 战斗内所有 `rng.roll/randint/chance` 必须显式传 salt
- 验收：同种子 + 同提交序列 → 逐位相同；回溯后重放一致

## 七、时间与世界层（用户拍板：战斗不推进世界天数）

战斗内时间（厘息）**只存在于战斗会话内**，结束后丢弃：
- 不调 `_advance_days`，不推进年龄/寿元
- 战斗的代价由**灵气消耗 + 灵石花费 + 战败折寿**承担
- 理由：`_advance_days` 是整数天，30 息战斗不足 0.001 天；推进只会引入浮点边界

### 11.1 R3.1 实现中发现并修掉的三个真问题（教训记录）

1. **速度尺度错配**：旧 `battle_stats` 的 `speed = 8 + 档`（绝对速度），而新时间轴要求
   速度是**倍率**（1.0 基准）——否则平砍只有 22 厘息、敌人 50 厘息，窗口小到排不了招。
   已改为 `speed = 1.0 + 档×0.02`；敌人原始速度经 `enemy_speed_multiplier()` 折算（8→1.0）。
2. **`_advance_until` 死锁**：`land_t == clock.t` 时函数立即 return，导致时钟永不推进、
   敌方永不行动（表现为"打完一下战斗就停住"）。已改为按 `(时刻, 优先级)` 取下一事件，
   并在 `deadline` 处兜底推进。
3. **窗口关闭不变量**：`run_window` 返回时若 `next_t(player) <= clock.t`，前端会拿到
   "已到期但无窗口"的状态，无法继续。已加 `_close_window()` 保证返回时
   **玩家无未落地动作且 `next_t > t`**（单测已锁）。
