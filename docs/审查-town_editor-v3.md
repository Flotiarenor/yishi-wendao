## 1.5 叠加视图重做（用户反馈「效果不理想」）

### 现象与量化

原实现：叠加时把**所有要素都画成同一个 `#4a4a4a`**，再把分区色乘 0.6 盖上去。
抽出来算实际合成色（滑杆默认 0.45）：

| | 现状（叠加） | 分区差异 |
|---|---|---|
| 建筑 | `74,74,74` | Δ4 |
| 道路 | `74,74,74` | Δ4 |

- **建筑和道路像素完全相同** → 叠加视图里这两层根本不可分（"效果不理想"的直接原因）；
- 分区色盖上去只让灰块微微偏色，**分区之间 Δ 只有 2~4**，人眼读不出来。

### 根因：颜色机制本身行不通，不是参数没调好

分区表是「浅色 + 低 alpha」（如 `#c9a22755` = 浅金黄 + 33%）。算了整整一张
「要素不透明度 → 分区还剩多少」的扫描表：

```
要素不透明度 0.95 → 分区间最小色距 0    建筑/道路可分 354
要素不透明度 0.85 → 分区间最小色距 1    建筑/道路可分 317
要素不透明度 0.60 → 分区间最小色距 2    建筑/道路可分 223
要素不透明度 0.30 → 分区间最小色距 4    建筑/道路可分 112
```

**任何不透明度下，"隔着要素看分区色"的分区间色距都 ≤4**——想靠"给要素染上分区色"
来表分区，在数学上就不成立（浅色乘低 alpha，隔着不透明墨色只剩个位数差异）。

### 重做方案：分区单独一条视觉通道

| 层 | 画法 | 作用 |
|---|---|---|
| ① 分区底色 | 铺在**最下面**（`zoneStyles(zoneAlpha)`，不再额外乘 0.6） | 缝/空地里的色块 |
| ② 要素 | 按**正常墨色**画（建筑近黑、道路近白），整体 `tileAlpha`（默认 0.85） | 一眼分清建筑/道路 |
| ③ 分区边界线 | 分区变化处画 2px **实色**线（`zoneEdgeStyles()`，压在最上层） | 密城里也能读出分区范围 |

配套：

- 新增滑杆「要素浓淡」`#talpha`（默认 85%），与「分区浓淡」并列——**两个滑杆各管一层**；
- 新增开关「叠加时画分区边界线」`#zedge`（默认开）；
- 两者只在叠加视图显示（其它视图藏起来，避免"看着能调其实没用"）；
- 新增**分区图例** `#zlegend`（色块 + `r 居民区` …）——不图例的话那些浅色块等于没标。

修好后的实测（`check_town_editor.js` 直接断言编辑器提交给 canvas 的颜色）：

```
编辑器实画颜色：✓ 建筑墨色 rgba(27,27,27,0.85)  ✓ 道路墨色 rgba(242,242,242,0.85)
                ✓ 分区底色 rgba(201,162,39,0.15) ✓ 分区边界线 rgba(201,162,39,0.92)
关掉「分区边界线」后还画边界线吗：✓ 不画了      切回要素视图后有没有残留分区色：✓ 没有
```

### 修复过程中自己踩的两个坑（都已加注释防复发）

1. **`hex.length < 9` 判"是否带 alpha"是错的**：普通 `#rrggbb` 是 7 字符，
   该条件恒为真 → 每次都 `return hex`，叠加视图一动不动（改了等于没改）。
   最终改成按**实际支持的两种写法**解析（6 位 / 8 位十六进制），不靠长度大小写。
2. **依赖全局变量的函数不好测**：`tileStyleOf` 原先读全局 `view`/`tileAlpha`，
   测试里把函数摘出来调用就静默走错分支。改成显式传参（默认取全局），
   并在 `check_town_editor.js` 里加了"编辑器实际画了什么颜色"的端到端断言
   （stub 现在记录每次 `fillRect` 的 `fillStyle`）。

配色对比图（A 现状 / B 半透明要素 / C 底色+边界线 / D 只有边界线）：
`docs/images/叠加视图配色对比.png`（用 `node tools/_overlay_preview.js` 可再生成）。

## 1.6 第二轮反馈：CPU 起飞 + 「8/8 个城门没有路」

### A. CPU：一帧 6500 次 canvas 调用，且**挪一下鼠标就全重画一遍**

实测（`node tools/measure_draw_cost.js tools/_user_town.json`，用你自己的青石镇）：

| 场景 | 每帧 canvas 调用 |
|---|---|
| 要素视图（网格线开） | 4258（其中 2304 是网格线） |
| **叠加视图（含分区边界线）** | **6453**（其中 1228 是上一版新加的分区边界线） |

更关键的是：旧写法**每次 `pointermove` 都把这一整套重画一遍**。鼠标快速划过时一秒能触发
上百帧，一帧 6500 次调用 × 上百帧 = 每帧实打实几毫秒的 CPU，风扇自然起来。
（`scheduleDraw()` 只做了 rAF 合帧，没有做"这帧到底需不需要重画"的判断。）

### 改法：分三层 + 脏标记

| 层 | 画在哪 | 什么时候重画 |
|---|---|---|
| ① 静态地图（分区底色/要素/网格线/分区边界线） | **离屏 canvas** | 只有 `markMapDirty()` 之后 |
| ② 光标框 | **叠层 canvas** | 换格时，只 4 条细矩形 |
| ③ 形状预览 | 主画布 | 只在拖拽那几帧 |

- `mapDirty` 标记接在所有会改变画面的地方：`setTile/setZone`（内容）、`setView`（视图）、
  `zoneAlpha/tileAlpha`（浓淡）、`showZoneEdge`、`showGrid`、缩放/改尺寸；
- `scheduleDraw()` 增加判断：**地图没脏、光标还在同一格 → 直接不画**；
- 没有离屏 canvas 的环境自动退回旧路径（每次都重画），不会白屏。

实测结果：

```
叠加视图换视图那一帧：8763 次调用（6452 格重画，这是必须付的钱）
之后每一帧：6 次调用（2 次 drawImage 贴图 + 4 条光标边）
相比改造前的 6453 次/帧：约 1076× 的下降
主画布内容：非白 6685/6724（99.4%），地图真的画出来了 ✓
缓存失效链：改内容/改视图/改浓淡/改边界线开关，全部会重画 ✓
```

### B. 「8/8 个城门内外两侧没有路」是**假警报**（第三个错判据）

你的图里 8 个城门**全部有路可走**（`tools/run_town_diagnose.js` 逐个打印过邻居）：

```
(23,2) 上+ 下+ 左= 右G  → 有路可走      (2,23) 上= 下G 左+ 右+  → 有路可走
(24,2) 上+ 下+ 左G 右=  → 有路可走      (45,23) 上= 下G 左+ 右+ → 有路可走 …（8/8 全部可走）
```

错在**判据按坐标猜门的朝向**：

```js
const vert = (y === 2 || y === H-3);        // 这是"门在**横墙**上"（墙在门的上下）
const ok = vert ? (上下有路) : (左右有路);   // 但横墙上的门的通路恰恰是**上下** → 查反了
```

`y===2` 说明门在横墙上、人应该从**上下**进出，分支却去查左右邻居。左右当然只有墙和另一个门格，
于是 8/8 全报错。**正确做法根本不用猜朝向**：门能走人的前提就是"四正方向有一侧挨着路"。

修好后：你那 8 个门全部通过，且"门四面真的没路"仍然报得出（回归测试覆盖三种情形：
门上下有路 ✓ 不报 / 门四面无路 ✓ 报 / 只有斜向有路 ✓ 仍算不通）。

### C. 顺带修掉：`setView(v)` 的形参遮蔽

```js
function setView(v) { view = v; ... }   // ← v 是形参，view = v 赋给了参数自己
```

**真正的 `view` 永远不变**，于是点「叠加 / 分区 / 要素」按钮和 `V` 键都"看着没反应"。
（这是我上一轮加 `markMapDirty()` 时引入的：参数名与全局同名。
现在参数改名 `next`，并留了注释防复发。）

### D. 回归测试新增

`tools/check_town_editor.js` 增加了：
- 城门判据三情形（门上下有路 / 四面无路 / 只有斜向有路）；
- 叠加视图**实际提交给 canvas 的颜色**（建筑 `rgba(27,27,27,0.85)`、道路 `rgba(242,242,242,0.85)`、
  分区底色 `rgba(201,162,39,0.15)`、分区边界线 `rgba(201,162,39,0.92)`）；
- 「分区边界线」开关是否真的生效、切回要素视图有没有残留分区色。

`tools/measure_draw_cost.js` 自带一个**会真写像素**的 mini canvas（含 alpha 合成与 `drawImage`），
用来断言"离线层真的画进了主画布"而不只是"调用次数少"——它自己也踩过两个坑
（`#fff` 简写没解析、width/height setter 无条件重建缓冲），现在都按浏览器行为实现了。

## 一、必修 bug

### P0-1 三个元素 id 重复 → 右侧面板的「导入」是死的

`aside` 与 `main>.panel2` 各写了一份导入区，`id` 完全重复：

| id | 第一次（aside，生效） | 第二次（panel2，被忽略） |
|---|---|---|
| `importFile` | 行 132 | 行 174 |
| `fileInput` | 行 133 | 行 175 |
| `out` | 行 139 | 行 179 |

`document.getElementById` 只返回第一个，脚本第 978~994 行的事件全部绑在 aside 那两份上。
结果：**右侧面板的两颗按钮点了没反应，右侧那个 `<pre id="out">` 永远显示不出导出结果**，
而 `document.getElementById("out").textContent = ...` 写的是看不见的左边那个（在 aside 里）。

修法：删掉 panel2 里重复的导入控件，并给右侧 `<pre>` 加一个「导出结果」小标题，
明确它只是"看结果的地方"，导入按钮留在左侧一处。

### P0-2 编辑器与引擎的判据不一致 → 导出的「体检结果」会骗人

1. **`on_road`（设施可达性）方向集不同**
   - 引擎 `Facility.on_road`：只走**四正方向**，`r = 1..2`；
   - 编辑器 `facilitiesDetailed()`：`dx, dy ∈ [-2, 2]` → **5×5 方框**，斜向也算。

   实测（抽算法单跑）：

   | 场景 | 编辑器 onRoad | 引擎 onRoad |
   |---|---|---|
   | 只有斜对角 (6,6) 有路 | `true` | `false` ★ 分歧 |
   | 正方向 (7,5) 有路 | `true` | `true` |

   即：**斜向贴路的坊市，编辑器说「通」，引擎说「走不到」**。

2. **设施种类少一个 `G`**
   引擎 `FACILITY_CHARS = {M, I, L, R, p, G}`（城门也算设施），
   编辑器只列 `M/I/L/R/p`。

修法：新增 `roadDistMap()`（从所有道路做 BFS，只走四正方向、深度到 2），
`on_road = dist ≤ 2`，与引擎逐字同口径；设施表补 `G 城门`。

**修复后实测（同一张已存模板，两边独立算）：**

| | 编辑器（改后） | 引擎 `facilities()` |
|---|---|---|
| 坊市 | 2 | 2 |
| 客栈 | 13 | 13 |
| 藏经阁 | 2 | 2 |
| 静室 | 2 | 2 |
| 广场 | 3 | 3 |
| 道路连通段（最大段格数） | 4 段（759） | 4 段（759） |

差集为空。改之前的编辑器在这张图上会少算多处设施，且 `on_road` 会出现假"可达"。

### P0-3 「城墙被路撞穿」检测写死 `y === 2 / y === H-3`（**并且旧口径是误报源**）

```js
for (let x = 2; x < W - 2; x++) { if (grid[2][x] === "+") holes++; if (grid[H-3][x] === "+") holes++; }
```

这是把 `genWall()` 的 `m = 2` 当成全图公理。实测：

```
墙在 y=4，旧口径 holes = 0        ★ 手画墙完全漏报
新口径（按格子自身判）= [(19,4),(20,4),(21,4)]  ✓
```

**更糟的是反过来的方向**：`+` ≠ `=`，城门位置的墙格**本来就被道路取代了**。
拿仓库里已存的青石镇（`content/town_layouts.py` 的 `_EXPORTS[0]`）实测：

```
旧口径：12 处 [(23,2),(24,2),(25,2),(23,45),(24,45),(25,45),(2,23),(2,24),(2,25),(45,23),(45,24),(45,25)]
新口径：0 处
y=2  x=20..28: ===+++===     ← 三段路正是南/北主干街穿墙的位置，墙本来就该在这里开
```

也就是说，存档里那条 `"城墙被道路直接穿过 12 处"` 是**假警报**：
穿过的是**通向城门的引路本身**。旧口径等于"城门 = 撞穿"，
只要城门开到墙线上就一定中招（这份图数量对得上 `gates=8`：南北主街 2×3 格 + 东西 2×3 格）。

修法：`wallBreaches()` 按格子自身判——某格 `=` 若"左右都是路"或"上下都是路"，
才算路从墙上穿过去。任意墙位都成立，`genTidy` 的补门路与体检复用同一套 `gateAxes()`。

> 附带结论：`content/town_layouts.py` 里存的 `errors` 文案与 `warnings`（"客栈：2/39 格…"）
> 都是旧口径的产物，下次动这份模板时应该一并重算。本次**没有改 content，也没改存档**。

### P0-4（审查中新发现）`genTidy` 补的设施连接路自己会变成新孤岛

原顺序是：① 删孤岛建筑 → ② 补门路 → ③ 接孤岛 → ④ 给设施拉路。
第 ④ 步在 ③ 之后执行，而它可能接的是**另一段路**而不是主网：

```
修前实测：接回后 道路段数 = 2
  段1: [(6,5),(7,5),(8,5),(9,5)]        ← 第 4 步为客栈新铺的连接路
  段2: [(10,6),(10,7),(10,8),(10,9),(10,10),…]  ← 主网
修后实测：道路段数 = 1  ✓
```

用户视角就是"点了清理，体检还是说有一段走不通"。修法：把接孤岛抽成
`joinRoadIslands()`，第 ④ 步之后**再跑一次**；同时把"只扫四正方向 4 格"改成
"找最近的那条路"（旧写法扫不到 4 格就放弃，于是"体检说不可达、清理也修不好"）。

### P1-1 撤销跨过「应用尺寸」后，宽高输入框骗人

`restore()` 里只改 `W/H` 与 canvas，没有同步 `#gw / #gh / #gz`，于是撤销回 20×20 后
输入框还写着 30×30，再点一次「应用尺寸」就把尺寸设回错的。
另 `W = grid[0].length` 没做行列校验，`grid`/`zones` 一旦不等长，
`drawCell(x, y)` 会抛 `TypeError`。

修法：加 `syncSizeInputs()`（`restore` / 导入 / 缩放快捷键 / 应用尺寸都走它）；
`restore()` 按 `grid` 与 `zones` 的**实际最长行**重建两个数组，越界读返回 `"."`。

### P1-2 空操作也占撤销栈（用户体感：按了 Ctrl+Z 没反应）

`pointerdown` 无条件 `pushUndo()`：点一下**已经画好的格子**、点击落在网格外、
拖一个 0 格的方框，都会塞进一条与当前状态完全相同的快照。

修法：改成 `beginGesture()`（先存"改动前"快照）+ `endGesture()`（真改了才入栈），
`setTile/setZone` 只在值真的变化时置 `moved`。

### P1-3 粘 JSON 到导出文本框里会被吞掉

`#out` 是 `<pre contenteditable="true">`，tagName 是 `PRE`，不在 paste 排除名单里，
于是"粘进文本框再点导入"的用法自相矛盾（粘贴被拦、直接触发自动导入）。
修法：加 `t.isContentEditable` 判断；顺带在可编辑文本框里也别抢 `Ctrl+Z`。

### P1-4 指针在画布外抬起 → 拖拽状态卡住

`pointerup` 只绑 canvas。修法：`window` 上补 `pointerup`、
`pointercancel`、`blur` 各一份收笔。

### P1-5 点/拖落在网格外会越界（边缘 1px）

`cvwrap` 有 1px 边框，`cellOf` 直接 `floor`，最右/最下 1px 按下会得到 `x >= W`，
`setTile` 自己会挡，但 `drawCell(x, y)` 会直接崩。
修法：`cellOf()` 统一 clamp 进网格；另留 `cellOfRaw()` 给需要原始坐标的场景。

### P2-1 画设施会把该格分区悄悄清掉

`if (v !== "." && v !== "+") setZone(x, y, "")` 是合理设计，但**完全静默**。
修法：`endGesture()` 统计本次清掉几格分区，状态栏附一句「（顺带清掉 N 格分区）」。

### P2-2 「应用尺寸」一键清空全图，无二次确认

修法：`confirm()` 明确写出"改成 W×H，会清空两层，可用 Ctrl+Z 撤销"。
「清要素 / 清分区」同样加了确认。

### P2-3 `genFill` 的注释与代码矛盾

```js
if (c === "T") continue;   // 树林也算城内空地（会被填）
```

代码是"树林挡住洪泛"，注释是"树林算空地"。实际行为（保留树林）才对——树林是景物。
改注释，不改行为。另外：城心若正好是墙/树/建筑，洪泛会从"城心那一格"起步失败，
现在会就近找一个能站人的格子作起点；洪泛区域超过全图 75% 时状态栏会警告"城墙没闭合"。

### P2-4 油漆桶的栈序不是真正的 DFS（**未改**）

`bucket()` 把邻居全 `push` 再 `pop`，能正确连通、不漏格，但 `st` 峰值不受控。
120×120 全图同色时峰值可达数万。不是必崩，留作后续清理。

### P2-5 `genTidy` 第 3 步是 O(孤立格 × 主网格)（**部分优化**）

已加"距离 1 就跳出"的剪枝；大图 + 多碎段时仍建议改"主网格分桶"。

## 四、结论

- 结构上没问题：两层网格 + 三档视图 + 生成器 / 体检 / 导入导出的分工是清楚的。
- 真正会伤到用户的是 **P0-1（右侧导入按钮是死的）**、
  **P0-2（体检判据与引擎不一致）**、**P0-3（写死墙位置，且旧口径把城门当撞穿）**，
  以及审查中新发现的 **P0-4（清理完还剩孤岛）**。
- 修完之后，同一张已存模板上编辑器与引擎的设施计数、道路分段**完全一致**；
  「城墙被路撞穿」从 12 处假警报变为 0 处真实撞穿（该图的墙并没有被撞穿）。
- 功能上最该补的是**自动保存**和**导出 PNG**，其次是撤销按钮与笔刷尺寸。


### P0-1 三个元素 id 重复 → 右侧面板的「导入」是死的

`aside` 与 `main>.panel2` 各写了一份导入区，`id` 完全重复：

| id | 第一次（aside，生效） | 第二次（panel2，被忽略） |
|---|---|---|
| `importFile` | 行 132 | 行 174 |
| `fileInput` | 行 133 | 行 175 |
| `out` | 行 139 | 行 179 |

`document.getElementById` 只返回第一个，脚本第 978~994 行的事件全部绑在 aside 那两份上。
结果：**右侧面板的两颗按钮点了没反应，右侧那个 `<pre id="out">` 永远显示不出导出结果**，
而 `document.getElementById("out").textContent = ...` 写的是隐藏不了也看不见的左边那个。

修法：删掉 panel2 里重复的导入区（已删，见下节「已改」），保留单一职责的一份。

### P0-2 编辑器与引擎的判据不一致 → 导出的「体检结果」会骗人

1. **`on_road`（设施可达性）方向集不同**
   - 引擎 `Facility.on_road`：只走**四正方向**，`r = 1..2` → 路必须在正东/正西/正南/正北 2 格内；
   - 编辑器 `facilitiesDetailed()`：`dx, dy ∈ [-2, 2]` → **5×5 方框**，斜向也算。

   实测（抽算法单跑）：

   | 场景 | 编辑器 onRoad | 引擎 onRoad |
   |---|---|---|
   | 只有斜对角 (6,6) 有路 | `true` | `false` ★ 分歧 |
   | 正方向 (7,5) 有路 | `true` | `true` |

   即：**斜向贴路的坊市，编辑器说「通」，引擎说「走不到」**。导出 JSON 里的
   `diagnostics.warnings` 与 `facility_detail[].on_road` 都会被存进 `content/town_layouts.py`，
   于是存档里的判断和运行时不一致。

2. **设施种类少一个 `G`**
   引擎 `FACILITY_CHARS = {M, I, L, R, p, G}`（城门也算设施），
   编辑器 `facilitiesDetailed()` 只列 `M/I/L/R/p` → 导出的 `facilities`/`facility_detail` 少城门，
   与 `TownLayout.stats()` 对不上号。

### P0-3 「城墙被路撞穿」检测写死 `y === 2 / y === H-3`

```js
for (let x = 2; x < W - 2; x++) { if (grid[2][x] === "+") holes++; if (grid[H-3][x] === "+") holes++; }
for (let y = 2; y < H - 2; y++) { if (grid[y][2] === "+") holes++; if (grid[y][W-3] === "+") holes++; }
```

这是把 `genWall()` 的 `m = 2` 当成了全图公理。用户手画墙（更内缩、或只画一面墙）时：

实测（墙在 `y = 4`，路真的撞穿）：

```
[5] 墙在 y=4 时，编辑器 holes 检测 = 0 → ★ 漏报（固定 y===2 假设）
```

`genTidy()` 第 2 步「门旁补路」同样写死 `y === 2 || y === H - 3` 判门的朝向，
`diagnose()` 判城门内侧有没有路也用同一套——**手画的门会被判成横向门**，补错方向。

修法：改成「按格子本身判断」——`=` 或 `G` 的格子，若左右任一侧是 `+`，即视为被撞穿/门朝向。

### P1-1 撤销跨过「应用尺寸」后，宽高输入框骗人

`restore()` 里只改 `W/H` 与 canvas，没有同步 `#gw / #gh / #gz`：

```
[6] restore() 里只改 W/H 与 canvas，未同步 #gw/#gh 输入框、未 updateStatus → 面板显示旧尺寸
```

另外 `restore()` 里 `W = grid[0].length` 没做长度校验——只要 `grid` 与 `zones` 行列不等长，
`blank()` 之外的一切（导入畸形 JSON、外部改数组）都会让 `drawCell(x, y)` 抛
`TypeError: Cannot read properties of undefined (reading 'x')`。属于脆弱点，一并加固。

### P1-2 空操作也占撤销栈（用户体感：按了 Ctrl+Z 没反应）

`pointerdown` 里无条件 `pushUndo()`：点一下**已经画好的格子**、点击落在网格外、
拖了一个 0 格的方框，都会塞进一条与当前状态完全相同的快照。
用户连按 Ctrl+Z 会「空转」几次才看到变化。

### P1-3 粘 JSON 到导出文本框里会被吞掉

```js
document.addEventListener("paste", (e) => {
  const t = e.target;
  if (t && (t.tagName === "INPUT" || t.tagName === "SELECT" || t.tagName === "TEXTAREA")) return;
```

`#out` 是 `<pre contenteditable="true">`，tagName 是 `PRE`，**不在排除名单里**。
用户想「粘进文本框再点导入」时，粘贴被 `preventDefault()` 拦截、直接触发自动导入，
文本框里反而没有内容——和页面提示的用法自相矛盾。
修法：加 `t.isContentEditable` 判断。

### P1-4 指针在画布外抬起 → 拖拽状态卡住

`pointerup` 只绑在 canvas 上（靠 `setPointerCapture` 兜底）。
若捕获被浏览器丢弃（触摸手势、某些指针设备、`pointercancel`），`drag` 永远是旧值，
下一次拖形状会把上一次的锚点连进来。修法：`window` 上补 `pointerup`/`pointercancel`。

### P1-5 点/拖落在网格外会越界（边缘按下时）

`cvwrap` 有 1px 边框，`cellOf` 直接 `Math.floor((clientX - r.left) / Z)`，
在最右/最下 1px 带按下 → `x >= W` → `setTile` 自己会挡掉，但 `drawCell(x, y)` 会**直接崩**。
修法：`pointerdown`/`pointermove` 统一 clamp 到 `[0, W-1] / [0, H-1]`。

### P2-1 画设施会把该格分区悄悄清掉

```js
if (v !== "." && v !== "+") setZone(x, y, "");   // 画 M/I/L/R/p/T/G/=
```

`drawShape` / 笔画 / 油漆桶都是这个行为，但**没有任何提示**，用户会以为分区丢了。
（设计上「设施格不该有分区」是合理的，问题是静默。修法：状态栏给一句统计。）

### P2-2 「应用尺寸」一键清空全图，无二次确认

`document.getElementById("apply").onclick` → `blank()`。8×8 输错一位，整张镇没了。
（撤销能救，但用户第一反应是「完了」。）修法：`confirm()`。

### P2-3 `genFill` 的注释与代码矛盾

```js
if (c === "T") continue;   // 树林也算城内空地（会被填）
```

代码是「树林挡住洪泛」，注释是「树林算空地」。实际行为（保留树林）才是对的——
树林是玩家要看的景物，不该被建筑埋掉。改注释，不改行为。

### P2-4 油漆桶的栈序不是真正的 DFS，且无 visited 数量上限

`bucket()` 把邻居全 `push` 再 `pop`，是「插到底再取」的混合序，本身能连通（不会漏格），
但 `st` 的峰值规模和推送次数都不受控；120×120 全图同色时峰值可到数万。
不是必崩，属于该加边界的写法。

### P2-5 `genTidy` 第 3 步是 O(孤立格 × 主网格)

```js
for (const [ax, ay] of comps[ci]) for (const [bx, by] of main) { ... }
```

48×48 尚可，120×120 且道路碎成多段时会明显卡顿（百万级内层循环 × 12 轮）。
可用「主网格按 8×8 分桶，只比邻近桶」降到近似线性。

## 四、结论

- 结构上没有设计问题：两层网格 + 三档视图 + 生成器 / 体检 / 导入导出的分工是清楚的。
- 真正会伤到用户的就两条：**P0-1（右侧导入按钮是死的）** 和 **P0-2（体检判据与引擎不一致）**；
  其次是 P0-3（写死墙位置）——它会让「体检通过」的图在引擎里仍然出问题。
- P1 级别的四条都是「用着用着突然不对劲」类型，改动量很小，建议一起修。
- 功能上最该补的是**自动保存**和**导出 PNG**，其次是撤销按钮与笔刷尺寸。
